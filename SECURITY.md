# Security Policy

## Reporting
Report vulnerabilities privately via **GitHub Security Advisories**: open the
repository's **Security** tab and use **"Report a vulnerability"**
(<https://github.com/Robbes/Ownpace/security/advisories/new>). If you have no
GitHub account, write to **support@ownpace.eu** instead. These are the only
two channels, in that order, and the site's `/.well-known/security.txt` names
the same two. Do not open public issues for security reports.

We acknowledge a report within **five working days**. We do not promise when
a fix lands; we tell you what we found and what we will do about it.

## Scope
- **The code in this repository**, both editions: the appliance and the
  managed service.
- **The hosted service**: `ownpace-live` at the `ownpace.eu` names during the
  Alpha, and the test stack at the `ota.ownpace.eu` names.
- **Testing against the hosted service needs the owner's permission first**,
  because it holds testers' credentials for their accounts. Ask through one of
  the channels above. Anyone can bring up a stack of their own to test instead:
  `docs/selfhost-quickstart.md` for the appliance, `docs/managed-bring-up.md`
  for the managed service.

## Supported versions
`main`, and the release the hosted service runs. There is no release line
yet: a fix lands on `main` and reaches the hosted service with its next
release.

## Principles
- **Secrets** never live in git; `.env` is gitignored, and gitleaks reads every commit a pull request adds before it can merge: a finding fails it (`ci.yml`'s `gitleaks` job), test files' fake tokens and one placeholder document aside. OAuth tokens, API keys and database credentials are stored **AES-encrypted in the ledger, under a key supplied as `SECRET_ENCRYPTION_KEY`**; no vault integration exists. That gives encryption at rest and no plaintext in git, but **no rotation, no per-secret access policy, and no audit trail of secret reads**, and the master key lives in the environment of the process that uses it. A vault (OpenBao/Infisical) remains the intended step; the trigger is a deployment with more than one operator to isolate, or a compliance review that requires it — which is also when it will be clear which vault.
- **Least privilege** for source access (O365 Application Access Policy scoped to in-scope mailboxes; read-only for one-way mirror).
- **Non-destructive defaults**; deletions never auto-propagate.
- **Tenant isolation** in the managed edition: Postgres row-level security, per-tenant rate budgets, and each organisation's stored credentials in its own rows, all encrypted under the one `SECRET_ENCRYPTION_KEY`. **Row security is in force on the API's request path, in the per-tenant background tasks and in every organisation's own reads of three scheduled jobs, and not in the three scheduled jobs that span organisations whole, which run as a system role that is not a superuser.** The eight per-tenant jobs (a sync pass, a discovery, a verification, a confirmation, an apply, a cutover's preparation, a rollback) connect as the application role. Three scheduled jobs, the digest, the drift detector and group discovery, are split: they read the list of active organisations, ids only, on a connection that sees every organisation, and read and write each organisation's own rows as the application role, in that organisation's scope. The other three scheduled jobs (the sync tick, retention, the purge of closed organisations), the split jobs' list and every job's audit key connect as the system role (`ownpace_system`): it bypasses row security, which questions across organisations need, so there the separation between organisations rests on each query's own tenant filter; it is not a superuser, may create no role or database, belongs to no role and has no role belonging to it, and holds only the grants those statements need, a grant to PUBLIC counted as one of them; the bring-up and the upload of the task environment each refuse to hand out its connection string when Postgres says otherwise, and every bring-up clears any setting left on the role, which an ordinary role may change on itself. No job's run receives the database owner's connection string. Every run holds the encryption key and the system role's connection string: on pg-boss each run is a process of the `worker` service, which has both from compose, one environment for every run; in trigger mode, the fallback, the task platform stores variables per environment. The job queue the managed edition keeps in the ledger's database, pg-boss's schema `pgboss` (ADR-0054), which the worker and the API connect to, belongs to a role of its own, `ownpace_jobs`: no superuser, no `BYPASSRLS`, a member of no role, owning that schema and nothing else, with no privilege on any table of the ledger. Its tables hold ids, no organisation's rows, and carry no row security; no other role is granted them, and the bring-up refuses the role when Postgres says otherwise. `docs/rls-guide.md` ("Where row security holds today") lists every connection. Taking the connection across organisations out of the runs altogether waits until the service admits people the owner has not let in personally.
- **Trust boundary:** data-plane workers may briefly hold plaintext during copy - minimize at-rest staging, encrypt spool, short TTL, TLS everywhere. Proton Bridge (if used) is self-host/local only.
- **The browser** (managed): the app is served with a Content-Security-Policy that runs its own scripts and nothing inline or evaluated, lets it connect to its own origin and the sign-in host only, and lets no page frame it; with HSTS (one year, no preload), `nosniff`, `X-Frame-Options: DENY` and `Referrer-Policy: no-referrer`, so a grant or view link does not leave its page as a Referer. The API sends its own, through helmet. **The sign-in token is still kept in the browser's `localStorage`**, where any script running in the app can read it: the policy keeps an injected script from running and from sending to another host by `fetch`, and does nothing against code in the app's own bundle. It is not yet in a cookie no script can read, and the appliance's screens send no policy yet.
- **Self-hosted CI runner:** trusted workflows only (docker socket + root = RCE risk). It shares the machine and its Docker daemon with the hosted service, so during the Alpha no merge runs there: a push to `main` runs CI and Security Scan on GitHub's hosted arm64 runner, and the repository variable `CI_PUSH_ON_SELF_HOSTED`, set to `true`, sends them back. A pull request never runs there. What still runs `main` on it, on a schedule, is what needs the machine: the appliance's nightly E2E, the managed gate on the test stack and the live-target lane.
- **Supply chain:** dependencies pinned (every CI action by commit SHA) and kept current by Dependabot where it can read them, and what it ignores by name (the Trigger.dev SDK, plus some major versions) has its reason written in `.github/dependabot.yml`. Dependabot reads no file in `deploy/compose`, so the managed stacks' images, among them the Trigger.dev images, the identity provider and ClickHouse, are compared with their upstream every week instead (MinIO has no upstream left to compare with), together with the tasks' Node, `packageManager`, the Trivy and the osv-scanner the scan runs, the gitleaks CI reads a pull request's commits with, the cosign that signs the images and checks their signatures, the Atlas release CI's migration lint downloads and checks by its SHA-256 before running it, the stalwart-cli release the integration tests and E2E gates install the same way, and the binfmt, BuildKit and SBOM generator images the image build runs, each by its digest, and an issue is kept open while one is behind (`.github/workflows/idp-pin-watch.yml`); every image the stacks run, Ownpace's own at `:edge` and at the newest release among them, is scanned by Trivy every week, report only, with an issue kept open for each image whose operating system is past its end of life (`.github/workflows/security-scan.yml`); published images are signed (cosign keyless, by digest — verifiable against this repo's workflow identity); a CycloneDX SBOM is generated per commit and attached to every release. From 0.2.0-alpha.20 on, each published image also carries its own SPDX SBOM as an attestation in its index, and the release carries a copy per image and platform (`ownpace-<image>-<version>.linux-<arch>.spdx.json`): `bom.json` comes from the lockfile and lists the npm packages, including what is bundled into the web assets and the appliance's bundle, but none of the operating-system packages the images are built on; an image's SBOM comes from its filesystem and lists those, Debian's under api, worker and selfhost and Alpine's under web, with the npm packages installed in it, but cannot see inside a bundled JavaScript file. Read both. The database, pooler and GoAccess images are built where they run and published by no one, so they carry none; the weekly image scan reads them ([docs/release.md](docs/release.md) §3).

A lightweight threat model lives in the architecture document
(`docs/architecture/solution-architecture.md`, §17.1). A full threat-model
artifact does not exist yet. It is written when a customer's security review
asks for one, or for the first release that is not a release candidate,
whichever comes first.
