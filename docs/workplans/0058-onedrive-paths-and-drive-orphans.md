# Workplan 0058 — what a walk from the root cannot reach

> **In one line:** OneDrive source paths from Graph `parentReference`, not a nonexistent `path`, the drive read once through the root delta with files placed by parent id, and Google Drive orphan detection in `listOrphanedFiles` and `scripts/list-drive-orphans.ts`.

## Status — 2026-09-22 (update this block at the end of every session)

| Task | Status | Evidence |
|---|---|---|
| T1 the finding | ✅ **Stated 2026-08-17** | The owner asked whether items exist that are not under the root — "floating" — and how each source handles them. Reading the five file sources together answered that they all enumerate by walking DOWN from a configured root and that nothing counts what a walk cannot reach; it also turned up a defect that made the OneDrive connector unable to migrate any real drive. |
| T2 OneDrive: the phantom `path` | ✅ **Fixed 2026-08-17** | `GraphDriveItem` declared `readonly path: string`. **Microsoft Graph does not return that field** — a driveItem carries `parentReference.path` (`/drive/root:` at the root, `/drive/root:/Documents` below it) plus `name`, and nothing mapped one to the other. So `item.path` was `undefined` at runtime and the natural key fell through to `` `/${item.name}` `` for EVERY file: the whole tree flattened onto the root, and `/Work/notes.txt` and `/Personal/notes.txt` became one key — which the ledger's unique index turns into a hard stop. The unit fixtures **fabricated the field**, which is the whole reason 41 tests stayed green over a connector that could not work. Now `itemPath()` derives the key from `parentReference.path`, the fixtures carry real Graph payload shapes, and a regression test pins that two same-named files in different folders get distinct keys. |
| T3 OneDrive: what the walk missed | ✅ **Fixed 2026-08-17** | `listFolders` listed `/drive/root/children` once and never recursed, so only TOP-LEVEL folders were ever returned — and the sync loop migrates exactly what `listFolders` answers. It also omitted the root entry that every other file source emits (`{ path: '' }`), so files sitting directly in the drive root were in no collection at all. Both fixed: a depth-first walk via `/drive/items/{id}/children`, root included, with a 64-level guard because an unbounded recursion against a customer tenant is an expensive way to discover a loop. |
| T4 OneDrive: the third reader | ✅ **Fixed 2026-08-17** | `isRename()` compared `oldItem.path !== newItem.path` — two `undefined`s — so it answered FALSE for every rename it was asked about. It goes through `itemPath` now. The test that "passed" asserted an impossible state (name changed, path identical), which was only expressible while `path` was fabricated independently of `name`; replaced with the real cases (a move is a rename; identical name+parent is not; no derivable path is never called a rename). |
| T5 Drive: the orphan coverage check | ✅ **Done 2026-08-17** | `GoogleDriveSource.listOrphanedFiles()` — one paged, read-only `files.list` over `'me' in owners` asking for `parents`, reporting files with none. Drive is the one provider where a file genuinely floats (delete a parent without its contents, or create via API with no `parents`): the file stays owned and intact, reachable by search but by no path, hidden even in Drive's own UI behind `is:unorganized`. A walk from `rootFolderId` never sees it, so it was never migrated and never mentioned. Capped, and a hit cap says `capped: true` rather than passing a partial list off as all. Surfaced by `scripts/list-drive-orphans.ts`, which also says what to do about one (move it into a folder in scope). Only files the account OWNS — a file shared WITH the account has parents it cannot see and would read as orphaned forever. 3 tests. |

(b) **Mostly moot since T7:** a file placed by its parent's id takes its path from the walk's `name`s, which are not encoded. It still applies to the fallback, a path Graph reported. OneDrive's `parentReference.path` is NOT percent-decoded here. Whether Graph encodes it for names with spaces or `%` is a real-tenant question, and decoding a literal `%` corrupts the name (`webdav-trashbin.ts` documents the same trap) — the first live run settles it. (c) OneDrive keeps its leading-slash path form (`/Documents`) where the other file sources use root-relative (`Documents`); the delta URL builder needs it verbatim, so it is left alone and stated rather than quietly changed. (d) Dropbox Business team namespaces and OneDrive `sharedWithMe` remain unreachable by design — recorded in the matrix, not fixed here. |
| T7 OneDrive: the delta that did not say where, and a file listed once per folder above it | ✅ **Fixed 2026-09-22** — not yet proven on a live tenant | Found reading why the owner's first live Microsoft → Nextcloud preflight sat on *"Still counting: Files"*. Two faults against Microsoft's own documentation of `driveItem: delta`. **(1)** *"The parentReference property on items won't include a value for path … When using delta you should always track items by id."* T2's `itemPath` built every key from exactly that path and skipped a file without one with a log line, so on a drive answering as documented EVERY file was skipped: not on the preflight, not copied, on no screen. **(2)** A folder's delta is its whole subtree (*"starts enumerating the drive's hierarchy"*), and T3's walk returns every folder, so a file three folders deep was listed four times, and the preflight summed them. Each listing keeps its DIRECT children only, which is 0026 T1's own wording: *"a non-root folder only yields its own items"*. A file neither can place is counted `unreadable` once, by the root. A folder holding only subfolders reports `listedElsewhere`, which the sync loop's first-read rule now counts as a read (beside a reported removal). So it keeps a cursor instead of re-reading its subtree every pass. Measured on a fake that answers in the documented shapes: the old listing found **0 of 4** files; with paths on the delta it listed **9 items / 18,210 bytes for 4 files / 6,110 bytes**; now 4 and 6,110 either way. The walk is still one request per folder, one after another: this removes the double reading, not the walk. |

## What this is

A silent-under-migration audit that found one connector broken and one provider gap unreported.

The OneDrive defect is the one worth remembering: a type asserted a field the API does not
have, the fixtures asserted the same fiction, and 41 green tests certified a connector that
could not have migrated a single real drive correctly. Tests written against invented payload
shapes prove the code agrees with the test author, not with the provider — which is exactly
why every connector here is ⏳ until it has met a real endpoint.
