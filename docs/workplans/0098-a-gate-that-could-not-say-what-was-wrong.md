## What broke

`managed.yml` marks a variable it cannot run without as `${VAR:?message}`, and
compose interpolates the **whole file** before running anything. So one missing
variable fails **every** compose command, whichever services it names.

Run #36's `[data]` step — postgres, the pooler's lookup role, pgbouncer — failed
with:

```
error while interpolating services.zitadel.command:
required variable ZITADEL_MASTERKEY is missing a value
```

A true statement about a service that step does not start.

The cause is not in the repository. The self-hosted runner's persisted `.env`
predates #496 (which added Zitadel: `ZITADEL_MASTERKEY`, `ZITADEL_DB_PASSWORD`,
`ZITADEL_ADMIN_PASSWORD`) and #497 (which added the status page's `WEB_URL`).
**That is the ordinary condition after any change that adds a service**, not an
edge case — and both of those changes were mine.

## The pre-flight check that should have caught it

The workflow already had a step for exactly this class of problem. It listed
its keys by hand, with a comment spelling out the hazard in full:

> `PGBOUNCER_AUTH_PASSWORD` is here for a reason that is not obvious: compose
> interpolates the WHOLE file before running anything, so without it EVERY
> compose command against managed.yml fails — with a message about pgbouncer,
> on a runner whose actual problem is an .env that predates the pooler.

The lesson was understood, written down, and attached to a hand-maintained
list. Two later PRs added required variables and neither touched it.

**This is the third hand-maintained list to drift in three days** — `MOUNTS` in
0096, the `pull_request` trigger filters in 0097, and this. Same shape every
time: a description of the system, kept beside the system, with nothing checking
that the two agree. The fix is the same shape too — derive it.

## What the gate does now

The required set is read out of `managed.yml` itself, then filled from the two
files that already know the answers:

| Source | Supplies | Why it is safe to run every pass |
|---|---|---|
| `ensure-env-secrets.sh` | the secrets | It fills a **missing** key and refuses to replace a live one. Idempotent by construction. |
| `managed.env.example` | non-secret defaults | It is the file a human copies for a fresh deployment; using it here is the same answer, applied automatically. |

A variable in neither is a genuine gap, and the step refuses naming it — but T3
means that refusal should never reach a runner, because the build fails first.

### Persisting the `.env` back is not housekeeping

`ZITADEL_MASTERKEY` is the key the identity provider encrypts its own data with.
Generating a fresh one every run would strand every user the previous run's
instance held — the exact hazard `ensure-env-secrets.sh` keeps a refusal list
for. So the filled `.env` is copied back to the runner's persistent directory,
and the next run reuses the same values. The copy is additive: nothing above it
ever replaced an existing key.

## What T3 cannot do

It cannot see a runner's `.env`. A persisted file can still fall behind — that
is now the workflow's job, and it derives the same list from the same sources.
This asserts the sources **can** answer; it cannot assert anybody asked them.
