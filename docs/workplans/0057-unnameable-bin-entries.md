# Workplan 0057 — what a bin read could not name

## Status — 2026-08-17 (update this block at the end of every session)

| Task | Status | Evidence |
|---|---|---|
| T1 the finding | ✅ **Stated 2026-08-17** | The owner asked what should happen to bin entries "outside the configured root" and "with no chain", across all sources. Reading the four bin reads together showed they treated the two identically — skip, silently — and that **only one of them deserves it**. The rule was already written down, in mail: `reconcile.ts` drops a binned message with no Message-ID and earns the silence with the next sentence — *"those items are counted as `unkeyable` wherever they are listed in scope."* Skipping is honest exactly when the same object is accounted for somewhere the owner looks. The file connectors skipped without that second half. |
| T2 the two cases, split | ✅ **Done 2026-08-17** | **Out of scope** (a Drive parent chain topping out elsewhere, a Box ancestor chain that never passes the configured folder, a WebDAV location outside `rootPath`) stays silent and is now stated to be *not* a blind spot: an item outside the root was never copied, so no ledger row and no target copy exist — and `resolveDiscardedItems` re-checks against the ledger anyway (`if (!row) continue`), so a connector-side scope filter can only ever lose true positives, never prevent false ones. **Unnameable** (a permanently-deleted Drive ancestor or a file Drive names no parent for, a Box item with no `path_collection`, a Dropbox tombstone with no `path_display`, an empty WebDAV original location) is counted: those items probably WERE in scope, nothing counts them anywhere, and their cost is precise — the deletion is still found by absence-counting but its evidence drops from `trashed` to `inferred`, which ADR-0024 gate 3 refuses to apply. The owner meets a deletion whose apply action is missing, with nothing to explain it. |
| T3 one shape, four sources | ✅ **Done 2026-08-17** | `TrashListing { paths, unnameable, reason? }` on the `FileSource` port (`unnameable` REQUIRED — a connector that has thought about its bin states zero rather than leaving the question open, the 0046/0421 required-field lesson), and `DiscardedListing { keys, unnameable, reason? }` for the same answer once hashed. All four bin reads return it and each carries its own `reason` in the source's own words. `webdav-trashbin.ts` gained `classifyTrashbinLocation` (the existing `trashbinPathToKeyPath` is now a thin wrapper, so its tests and callers are untouched). `dav-sync` passes the count through; `domain-sync` logs it once per pass and carries it on `DomainSyncResult.unplaceableDiscards`, next to `excludedCollections` and for its reason: quietly losing a capability is the same class of failure as quietly using one. Mail returns `unnameable: 0` as a CLAIM, with the comment explaining why it can — an unkeyable message was never copied, so no target copy exists to act on. 9 tests (4 Box, 3 core end-to-end incl. the absent-when-clean case, plus the existing suites moved to the new shape). |
| T4 not done, honestly | ⛔ | (a) The count reaches the pass RESULT and the operator log; it does not yet reach the owner's Deletions queue UI or the completion report. That needs the count persisted per pass (a ledger column) rather than living only on the in-memory result — its own slice, and the shape above is what it would read. (b) Nothing yet *aggregates* the count across passes, so "3 unplaceable" on ten consecutive passes reads as ten separate facts. (c) The Graph/OneDrive `removed` path resolves ids via `findBySourceRef` and has the same "no row" case, but there it is genuinely out-of-scope-shaped (an id we never migrated), so it is left silent — stated here rather than discovered later. |

## What this is

A correctness-of-reporting change, not a behaviour change: no deletion is found or missed that
was not found or missed before. What changes is that the product can now say WHY an apply
button is absent, in the one case where the absence is caused by something the owner cannot
see. The rule it generalises was already in the codebase — mail wrote it down first, and the
file sources simply had not been held to it.
